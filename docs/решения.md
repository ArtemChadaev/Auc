## Архитектура
- луковоая, но в 1 папке все слои связанные с 1 областю, сделанно для удобства решения 1 задачи или crud
- Вот в 1 папке только 4 файла начинаются на название папки. (На примере item, itemDomain -> itemRepo -> itemService -> itemHandler). И в этих папках все основные функции которые используют другой слой. Всё остально вспомогательные функции.
- В каждой папке свой Router(или несколько), в main все оши сливаются и дополняются middleware
- В cmd в папках всё что используют остальные папки и main
- migrate, пока не готова основа и не вылаженно в сеть, только init.sql который просто меняется. БД не тяжело удалить и новую поставить, после версии 1.0 начнётся стандартная миграция (когда не так много изменений будет)
- Папки будут идти по иерархии по смыслу использования (По факту как fk), тоесть lots может использовать функции item, но не наоборот, т.к. item не знает про lots. Все такие случаи отдельно пробрасывается в main. Может пробрасыватся толбько service (имя файла = имя папки, item = item)
- Все методы которые не используются в других пакетах с маленькой буквы (По факту всё писать кроме Router). если возникает необходимость (Как lots -> itemService), в отдельной функции (в виде просто названия папки) написать все нужные функции (Даже если такая функция уже есть просто функция вызывающая функцию)
- Желательно чтобы только handler имел доступ к функциям извне
- В 1 папке может быть несколько таблиц бд, если они связанны (новая таблица имеет только fk главной таблицы (или такой же таблицы), кроме uid, он может быть везде)
- Если что весь код go в 2 папках internal & cmd. frontend, migrations, docs говорят сами за себя. apiTest набор .http и js файлов при необходимости для тестирования api

### Ошибка
- Основная группа ошибок а так же их стиль лежит в apperr. В частности для handler будет своя кастомная ошибка. Только такую принимает writeError. Все общие будут лежать в apperr, остальные специфичные в handler где нужны.
- Если понадобится ошибка которая уже создана в другом месте надо проанализировать почему такая возможность понадобиласб. М.б. ошибка общая (если ошибка кода который реализует таблицу, к которой fk таблицы требуюзей её ошибку, то просто берем)
- Ошибка может реализовыватся чисто в middleware если только там она и нужна
- Ошибки в репозитории/сервисе отдельно выводятся только если их надо проверять (Для вывода клиента) или используются в разных пакетах. Иначе просто errors.New Для точного описания ошибки и Debug/Warn/Error для вывода ошибки
- Ошибка Ррепозитория и сервиса кастомные через appErr (В котором только ошибка а серьезность логирования (slog.Level))
- При возврате существующей ошибки используется fmt.Errorf("имяФайла.Метод: %w", err)
